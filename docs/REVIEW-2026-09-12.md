# Command Chroma verification report

Command Chroma 0.4.0 passes the available automated checks and the current
Omarchy command-line manifest validator. Its English installer, explicit Bash
consent, theme-aware rendering and documented update/removal behavior are
consistent with the inspected implementation. Native Omarchy desktop acceptance
remains open; the automated results do not establish Wayland focus, configured
terminal launching or multi-monitor behavior. This is a scoped engineering
review, not a security certification or proof that every possible setup works.

The reviewed starting point is `6ddb86674cc55afd115987b7a188ab5a0f9537c8`.
Runtime preparation and the expanded screenshot capture were verified at
`35df92190422b240573956ca314b45f126ae654f`. Both have successful GitHub Actions
runs. The accompanying publication changes add documentation and image copies
on top of that code; no tagged stable release or Marketplace admission is
implied by publishing the branch to main.[^1][^2]

## Compatibility with current Omarchy

The upstream comparison uses Omarchy Quattro commit
`31bd80daa4613ffdee995ac27467fce5a2990806`. Its shell contract accepts root
manifests with `kinds: ["bar-widget"]` and a `barWidget` entry point. Chroma's
manifest, entry-point paths and namespaced ID fit that contract; the upstream
validator was also run directly against this checkout and returned success.[^3][^4]

The reviewed `Ui.BarWidget`, `Ui.Panel`, `Ui.KeyboardPanel` and `Ui.BarIconButton`
still expose the properties and functions used by Chroma: bar injection,
controller open/close state, anchor/owner/focus targets, fitted content width,
capped height and a custom icon component. This supports source-level
compatibility, but cannot confirm how those surfaces behave on a particular
Hyprland version, bar orientation or monitor arrangement.[^5]

Omarchy's add command intentionally clones and validates plugin files and
optionally enables the widget. It does not execute plugin installation hooks
and it does not select an arbitrary development branch. Chroma therefore opens
its installer through the explicit **Set up in terminal** action. The README now
starts with the normal add command for main; the ZIP bootstrap also tracks main.
An existing checkout that still tracks the development branch needs the
documented one-time Git branch switch.[^3][^6]

The screensaver at the inspected upstream commit uses `ttfx`. Chroma invokes the
same engine for its own logo effect, without starting the full screensaver or
changing Hyprland cursor visibility. Terminal launching uses Omarchy's wrapper,
whose current implementation delegates to `xdg-terminal-exec` through the desktop
application launcher. A real device must verify that launch chain.[^7][^8]

## Installation and configuration behavior

The terminal review obtains passive status before asking for consent. It does
not source `.bashrc` or the executable Chroma configuration. Explicit setup runs
the bundled installer from the installed plugin revision, creates a pre-change
backup of an existing `.bashrc`, and manages only its marked loader block.
Malformed markers are refused. Existing configuration, supported `.bashrc`
symlinks and an existing disabled state are covered by the lifecycle tests.[^1]

The missing ble.sh dependency is fetched only during confirmed setup, using a
pinned release and SHA-256 verification. Setup does not install system packages
or invoke sudo. The development test runner installs its own tools in the CI
runner; those test dependencies are not prerequisites added to the end user's
machine by the plugin. Animation tools remain optional at runtime.[^1][^2]

Enable/disable changes affect new Bash terminals. A theme reload token requests
a refresh at the next prompt in shells already running Chroma 0.4; it does not
restart terminals or inject commands. Doctor creates its own diagnostic shell.
Removing the widget and removing the Bash integration are separate operations,
which is consistent with Omarchy not running plugin uninstall hooks.[^1][^3]

Plugins run inside an unsandboxed desktop shell, and the user's Chroma config is
executable Bash by design. Inspect/legend/doctor can evaluate that trusted config.
These behaviors are disclosed in README/security notes and in the prepared
Marketplace request. Test success does not make untrusted configuration safe.[^3]

## Screenshot evidence and visual limits

The installer image is a real xterm/Xvfb capture after the actual ttfx intro,
using the read-only preview's neutral sample paths. Root `preview.png` is an
exact copy for the Marketplace's preview slot. It contains no native desktop
claims or fabricated installation-success state.[^9]

Three new terminal images use real Bash, the pinned ble.sh and the shipped
Chroma layer. The example is typed into the actual editor with no Return key;
the package, network and Git commands shown are not executed. The legend above
the prompt is actual `chroma legend` output. The Catppuccin source is copied from
the pinned upstream theme; black and white use the existing test fixtures.[^2][^10]

| Terminal capture | Reported minimum for managed foregrounds | Interpretation |
| --- | --- | --- |
| Catppuccin | 7.083:1 | Colorful upstream palette remains readable on its dark background |
| Vantablack fixture | 6.327:1 | Monochrome hues remain visible on black |
| White fixture | 5.572:1 | Foregrounds remain dark enough on white |

These values describe the displayed capture sessions, not universal performance
on every theme. In particular, ordinary ble.sh syntax such as URL-link styling
is outside Chroma's contrast measurement. The captures visibly retain ble.sh's
blue URL style, which can be faint on dark backgrounds. Explicit user-defined
styles also override the contrast guard. The README now makes this boundary
clear alongside the images instead of implying that every terminal glyph has
the same contrast guarantee.

Dashboard images are actual Qt renders of the shipped component, but their
status/contrast values are deliberately supplied test fixtures. They are useful
for layout and button review, not evidence of a live Omarchy installation. The
native-desktop placeholder is retained, and the caption identifies what remains
to capture. All image provenance and replacement paths are listed in
`docs/images/README.md`.

## Remaining device work

Complete the detailed acceptance list in `docs/PLUGIN_TESTING.md`. The minimum
owner check is to update/install, open the panel's terminal installer, cancel
once, install deliberately, and run `chroma doctor` in a new Bash terminal.
Then check theme changes, Tab and Ctrl-R, enable/disable, panel Escape/outside
click, and multiple monitors if used. Preserve local Git changes before moving
an existing development checkout to main.

One new screenshot is still needed: the Chroma icon in the actual Omarchy bar
with the dashboard open. Save it as `docs/images/omarchy-desktop.webp`, without
personal paths or notifications, and replace the remaining README placeholder.
A native installer picture is optional because the real terminal installer is
already illustrated. The capture scripts cannot establish native Wayland
acceptance in this environment.

## Marketplace readiness

The repository is public, uses the MIT license, documents runtime dependencies
and contains a root manifest plus installation/removal instructions. The root
preview is an actual terminal image. The proposed category is Developer Tools;
the prepared request uses the accepted tags bar, quickshell and system.[^11]

Indexed searches found no matching permanent ID or existing submission for this
repository. They did find the distinct Chroma color-picker project, supporting
the more specific Command Chroma display name. The complete registry could not
be read through the connector because of its file size, so current/historical
ID availability must still be confirmed by the Marketplace's validation.[^12]

The prepared request is in `docs/MARKETPLACE_SUBMISSION.md`, with the title
`[Plugin]: Command Chroma`. It explicitly discloses the remaining native tests.
The submission guide requires owner approval of the finished text and all five
checklist statements before an agent posts it. Ownership/asset permission and
understanding of the listing-versus-security distinction remain for that final
confirmation. No issue has been posted by this review.[^11]

The Marketplace's current static baseline is a separate check against the exact
submitted commit. This review did not run or fabricate that official result.
Its policy distinguishes automated results from maintainer acceptance and does
not treat a listing as a security guarantee. Any remote-build or other reported
capabilities must remain visible to the maintainer.[^13]

The repository's separate GitHub About field was still empty when inspected.
README and manifest descriptions are updated; an empty About field does not
prevent plugin loading. A suitable optional summary is: “Theme-aware semantic
Bash highlighting for Omarchy, with an English terminal installer and a native
Quattro control panel.”
