# Chroma parser, installer and documentation review — 2026-10-19

This change implements all 14 supplied findings against `24bb81d` and adds
four corrections found during an independent code and documentation review.
It is an unreleased change; the plugin version remains 0.4.3. Marketplace
approval of the September 29 snapshot is not transferred to this revision.

## Independent review and implemented corrections

Exa research used six searches across three topics: shell/CLI semantics,
ble.sh integration/performance, and data preservation/accessibility. The
searches returned 30 results before deduplication. Findings below are based
on inspected source code and the linked primary documentation, rather than
the number or rank of search hits.

1. **Multiline comments hid later commands.** A comment previously consumed
   the complete editor buffer. Comments now end at the newline, so `rm` on
   the next line receives its danger style. This does not interpret words
   inside comments as commands. See the [Bash manual](https://devdoc.net/linux/bash-4.4.html).
2. **Python script arguments could impersonate pip.** `python report.py pip
   uninstall` previously looked like package removal. Only Python's module
   invocation (`-m pip` or `-mpip`) gets pip classification. See
   [Python command-line semantics](https://docs.python.org/3/using/cmdline.html).
3. **uv pip could receive contradictory styles.** `uv pip uninstall` now
   gives the executable, pip group and uninstall action the same remove
   category. See [uv package management](https://docs.astral.sh/uv/pip/packages/).
4. **Data named `delete` changed unrelated classifications.** `git push -f
   origin delete` previously lost its danger category; `git show delete`
   and `gh repo view delete` also looked like removal. Git arguments and
   GitHub command positions are now distinguished. Similarly, Docker
   arguments named `prune` or `delete` cannot turn inspection into removal.
   See [Git push](https://git-scm.com/docs/git-push) and
   [Docker Compose down](https://docs.docker.com/reference/cli/docker/compose/down/).

The GNU [xargs](https://man7.org/linux/man-pages/man1/xargs.1.html) and
[find](https://man7.org/linux/man-pages/man1/find.1.html) manuals were checked
for option arity, optional attached values and exec termination. In
particular, xargs `--show-limits` can still run a command and must not hide
it. The [pacman manual](https://man.archlinux.org/man/pacman.8.en) distinguishes
sync search, cache cleanup and print-only operations. Python's
[binary file APIs](https://docs.python.org/3/library/pathlib.html) support
the byte-preserving backup implementation.

## Validation

The local full suite passes with the prepared, pinned ble.sh and Omarchy
themes, Qt 6 and ShellCheck. It includes:

- 160 parser checks, including ordered, in-bounds spans at every prefix of
  representative commands; 44 theme checks including 22 pinned palettes.
- 25 bridge/lifecycle tests, 12 bootstrap tests, four local-source tests,
  and the oversized streaming-download test with both curl variants.
- 15 terminal-installer cases: 14 pass locally; the real ttfx case is skipped
  because the engine is not installed locally and remains required in CI.
- Nine Qt results with zero failures/skips and 13 real ble.sh PTY input tests.
- Actual ble.sh composed danger styles for force pushes, parameter-expansion
  chains, xargs, find execdir and combined sudo flags in dark and light themes.
- Bash syntax, ShellCheck and Ruff, including extensionless Python scripts.

The local environment is headless. These results do not establish native
Omarchy/Wayland focus, terminal launching or multi-monitor acceptance. Follow
the existing [device checklist](PLUGIN_TESTING.md).

### Timing sample

On this cloud worker, three batches per input were timed using Python's
monotonic clock around a fresh Bash process sourcing defaults and the parser.
Normal inputs were classified 100 times per batch; long inputs three times.
Values are median milliseconds per classification, including amortized process
startup. The old parser was extracted from `24bb81d`; no sample command ran.

| Input | Characters | Previous | Updated |
| --- | ---: | ---: | ---: |
| `sudo pacman -Syu firefox && git status` | 38 | 2.223 | 2.555 |
| `find . -execdir sudo -nu root rm -rf {} +` | 41 | 2.057 | 2.476 |
| echo with one long argument | 4101 | 142.215 | 147.968 |
| 80 git-status commands | 1116 | 135.145 | 127.406 |

These are diagnostic samples, not release thresholds or measurements of the
whole editor. The old parser did less semantic work for nested find commands.
Long-input latency is a concrete follow-up; a silent size cutoff would hide
dangerous commands and is therefore unsuitable as the default fix.
